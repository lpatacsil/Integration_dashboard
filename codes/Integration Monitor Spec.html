1. What we are asking for

One dashboard, with alerting, that answers two questions at a glance: are all integration transactions between NetSuite and Shopify (through TeamCentral) flowing in and out correctly, and if not, how bad is it and who has been told. A second panel covers transactions that reached NetSuite but failed inside NetSuite for reasons unrelated to the integration (Vertex tax, inventory item not recognized, validation, permissions).

A working prototype with sample data is published alongside this page. It implements the rules below in code so Larry can copy the logic, and it has a scenario switch so you can see what each severity level looks like before any real data is connected.

3. Error categories (the taxonomy)

Every logged failure is assigned exactly one code by matching the raw error text against a rule list, top to bottom. The group decides what happens next: MAPPING and INDEXING codes are integration-blocking and drive severity; NETSUITE codes go to the internal-log panel with thresholds; TRANSIENT codes are auto-retried and only reported if they repeat; OUTAGE is Sev 4.

CodeMeaningGroupMatch pattern (regex, case-insensitive)
MAP-CUSTCustomer not mapped / indexedMAPPINGcustomer.*(not (found|mapped)|missing)
MAP-ITEMItem / SKU not mappedMAPPING(item|sku).*(not (found|mapped)|invalid)
MAP-SHIPShip-to address not mappedMAPPING(ship.?to|address).*(not (found|mapped)|invalid)
MAP-LOCLocation / store not mappedMAPPING(location|store|shop).*(not (found|mapped))
IDX-SKIPRecord skipped by indexingINDEXINGskipped|no index|not indexed
TAX-VERTEXVertex tax calculation failedNETSUITEvertex|tax (calc|service)
INV-ITEMInventory item not recognized / insufficientNETSUITEinventory|insufficient|not recognized
NS-PERMPermission / role errorNETSUITEpermission|role|insufficient privilege
VAL-DATAValidation / required field missingNETSUITErequired|invalid value|validation (default if nothing else matches)
API-RATERate limit / timeout, auto-retriedTRANSIENTrate limit|429|timeout|timed out

The patterns are a starting point written against typical TeamCentral and NetSuite error wording. Larry should pull one week of real log text, run it through the list, and adjust the patterns until fewer than 5% of errors fall into the VAL-DATA default bucket.

4. Severity rules

Severity is evaluated on every refresh, per flow direction and overall (overall = the highest of any flow). It is computed from the set of open, unresolved, integration-blocking errors plus the connector's health.

LevelConditionMeaning
Sev 0No open blocking errors; heartbeat fresh; traffic within baseline.All flowing. Nothing to do.
Sev 1Exactly one transaction blocked by a MAPPING or INDEXING error.One order is stuck because a customer, item, ship-to or location is not mapped.
Sev 2More than one transaction blocked, all opened today.Several orders stuck; likely one missing mapping affecting many orders.
Sev 3More than one blocked and the oldest was opened before 00:00 today (unresolved into day 2).Backlog is aging; management is copied.
Sev 4Heartbeat older than 30 min, or zero transactions in the last 60 min while the 4-week baseline for this hour and weekday is greater than zero.Tool is down; nothing is moving in either direction.

Two rules of thumb. Severity never steps down automatically while an incident is open; it drops only when the blocking errors are resolved or re-run successfully. And a single blocking error that ages into day 2 stays Sev 1 under your definition, but it is flagged as an SLA breach in the incident table and re-notified on the Sev 1 cadence — worth deciding whether you want that to auto-promote instead.

4.2 Classifier (pseudo-code, any language)

category  = first CATEGORY_RULES entry whose regex matches the raw error text
blocking  = category.group in ("MAPPING", "INDEXING")

function classify(openBlocking, heartbeatAgeMin, txLast60, baselineLast60):
    if heartbeatAgeMin > 30 or (txLast60 == 0 and baselineLast60 > 0):  return 4
    n = count(openBlocking)
    if n == 0:                                                           return 0
    crossedDay = any(e.openedAt < startOfToday for e in openBlocking)
    if n > 1 and crossedDay:                                             return 3
    if n > 1:                                                            return 2
    return 1

4.3 NetSuite saved-search formula (if the log lives in a NetSuite custom record)

-- Formula (Text) column on the integration-log custom record
CASE
  WHEN REGEXP_LIKE({custrecord_tc_error}, 'customer.*(not (found|mapped)|missing)', 'i') THEN 'MAP-CUST'
  WHEN REGEXP_LIKE({custrecord_tc_error}, '(item|sku).*(not (found|mapped)|invalid)', 'i')  THEN 'MAP-ITEM'
  WHEN REGEXP_LIKE({custrecord_tc_error}, '(ship.?to|address).*(not (found|mapped)|invalid)', 'i') THEN 'MAP-SHIP'
  WHEN REGEXP_LIKE({custrecord_tc_error}, '(location|store|shop).*(not (found|mapped))', 'i') THEN 'MAP-LOC'
  WHEN REGEXP_LIKE({custrecord_tc_error}, 'skipped|no index|not indexed', 'i')             THEN 'IDX-SKIP'
  WHEN REGEXP_LIKE({custrecord_tc_error}, 'vertex|tax (calc|service)', 'i')                THEN 'TAX-VERTEX'
  WHEN REGEXP_LIKE({custrecord_tc_error}, 'inventory|insufficient|not recognized', 'i')    THEN 'INV-ITEM'
  WHEN REGEXP_LIKE({custrecord_tc_error}, 'permission|role|insufficient privilege', 'i')  THEN 'NS-PERM'
  WHEN REGEXP_LIKE({custrecord_tc_error}, 'rate limit|429|timeout|timed out', 'i')         THEN 'API-RATE'
  WHEN REGEXP_LIKE({custrecord_tc_error}, 'duplicate|already exists', 'i')                 THEN 'DUP'
  ELSE 'VAL-DATA'
END

De-duplication. An incident is keyed on flow + category + entity reference. An email goes out when it is first opened, again only when its severity level changes, on the re-notify cadence above while it stays open, and once when it resolves. A dashboard refresh never re-sends. Larry's alert job needs a small state table (incident key, current level, last notified at, resolved at) to make this work — the one piece of storage the alerting needs even if the dashboard reads TeamCentral live.

6. Data source: TeamCentral log vs NetSuite log

You asked whether the TeamCentral transaction log is enough or whether NetSuite's own logs are needed. The answer is both, for different halves of the dashboard.

  • Integration flows and severity (Sev 1–4): the TeamCentral transaction log is the right source, because it is the only place that sees a transaction that never reached NetSuite (an unmapped customer stops the order before NetSuite is involved) and the only place that knows the connector's heartbeat.
  • NetSuite internal panel: NetSuite is the source. Vertex failures, inventory errors and validation failures are raised by NetSuite when the record is saved. A saved search on System Notes / the integration custom record, or on the integration role's execution log, gives these directly.

Caveat on Larry's API request. TeamCentral's public developer documentation describes an OAuth 2 API Gateway with entity and message routes (for example POST /api/{entitytype}messages and GET /api/coreentities/{entitytype}) but does not document a transaction-log, run-status or error endpoint. Before Larry builds against an assumption, ask the TeamCentral account team three questions: is the transaction log queryable through the gateway or available as a scheduled export; can it emit a webhook on failure; and does it expose a heartbeat or last-run timestamp. If the answer is no to all three, the fallback is to have TeamCentral write each transaction outcome to a small NetSuite custom record (integration log) — then the whole dashboard, including severity, can be built as a Suitelet with saved searches, which is Larry's home ground.
